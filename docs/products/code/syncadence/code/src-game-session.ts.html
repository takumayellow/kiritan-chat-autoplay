src/game/session.ts

takumayellow/syncadence-v2 の main（404da56）の写し。コードは 1 文字も変えていない。右の解説はこのサイトだけのもの。

1 回のプレイの「どのノーツをもう叩いたか」「コンボはいくつか」「スコアはいくつか」を覚えておき、押した・離した・時間が経った、の 3 つの出来事から判定を出すファイルです。

このファイルが担うもの

  • 譜面の生のノーツ（RawChartNote）を、欄に名前の付いた PlayNote に作り直し、レーンごとの列に振り分ける（コンストラクタ L52-62）。
  • 押したときの判定 press（L90-111）。そのレーンで次に来るノーツとの時刻の差から、PERFECT〜MISS を決める。
  • 離したときの判定 release（L114-121）。ロングノーツを押している途中なら、終点を判定する。
  • 時間が経ったときの処理 update（L132-158）。叩かれずに通り過ぎたノーツを MISS にし、最後まで押し切ったロングノーツを成功にする。
  • 判定の数・コンボ・スコア・押した時刻のずれを数え（record L76-87）、画面と結果に渡す（hud L165、stats L173）。

判定の幅そのもの（±42 ms など）は src/game/judge.ts が持ち、このファイルはそれを使って「どのノーツに当てるか」「ロングノーツをどう数えるか」を決めます。音や時計には触れません。受け取る時刻は、呼び出し側の src/game/engine.ts が入力の補正まで済ませた「曲の位置（秒）」です。

読みどころ

  • レーンごとの列とカーソル（lanes と laneCursor）。押したレーンで「まだ判定していない最初のノーツ」だけを見るので、毎回全ノーツを探さずに済みます。
  • press の 3 通りの結末（L97・L101・L103-109）: 当てるノーツが無い／遠すぎて空振り／判定が付く。
  • ロングノーツは 2 つに数える（L61）。始点を press、終点を release か update で判定します。
  • realMs（L72-74）。テンポを落としても、判定の幅は実際の時間（ミリ秒）で同じにするための換算です。

落とし穴

  • 遅すぎる側の幅は実質 125 ms です。 早すぎる押下は 160 ms まで MISS として受け付けますが（judge.ts の L25）、遅れたノーツは update が 125 ms（WINDOWS.good）を過ぎた時点で見逃しの MISS にします（L148）。フレームとフレームの間に 125〜160 ms 遅れて押した場合だけ、press 側で MISS が付きます。
  • ノーツの番号が 2 種類あります。 PlayNote.index は JSON に書かれていた順番、クラスの中で i と書いている番号は時刻順に並べ直した後の順番です（L53-55）。stateOf(i) や holding は後者を使います。今の曲データはもともと時刻順なので 2 つは一致しますが、混ぜて使うと食い違う作りです。
  • 範囲外のレーンのノーツは黙って捨てられますが、総数には数えられます（L58 と L61）。すると判定数が総数に届かず finished が真にならず、曲が終わりません。これを防いでいるのは src/song/validate.ts の L78-79 の検査です。
  • judge.ts の breaksCombo は使っておらず、コンボを切る条件は L80 に judgement === "miss" と直接書いてあります。
  • isHolding（L68-70）は、このコミットではテスト（session.test.ts）からしか呼ばれていません。

文法: 引数の既定値

rate = 1 のように引数に = 値 を書くと、呼び出し側がその引数を省いたときに使われる値になります。new GameSession(notes, 4) と 2 つだけ渡せば、rate は 1 です。

文法: オブジェクトを返すアロー関数と、欄の省略記法

L54 の ([time, lane, duration, links], index) => ({ index, time, lane, duration, links }) を分けて読みます。

  • 引数の [time, lane, duration, links] は、受け取った 4 つ組の配列を、その場で 4 つの変数に分けて受け取る書き方です（文法の索引の『分割代入』）。
  • => の右の ({ … }) は、オブジェクトを作って返します。外側の丸括弧が要るのは、=> { と書くと { が「関数の中身の始まり」と読まれてしまうからです。
  • { index, time } は { index: index, time: time } の省略形です。欄の名前と変数の名前が同じときに使えます。

文法: sort と比較関数

配列.sort((a, b) => 数) は配列を並べ替えます。渡した関数は 2 つの要素 a・b を受け取り、a を前にしたいなら負の数、後ろにしたいなら正の数、どちらでもよければ 0 を返します。a.time - b.time は「時刻の早いほうが前」になります。

X || Y は、X が 0（など偽とみなされる値）なら Y を使う、という意味になります。a.time - b.time || a.lane - b.lane は「時刻で比べ、同じ時刻ならレーンの小さいほうが前」です。

sort は元の配列そのものを並べ替えますが、ここでは直前の map（文法の索引の『map・filter・reduce』）が作った新しい配列に対して呼んでいるので、受け取った raw は変わりません。

文法: Array.from で長さを決めて配列を作る

Array.from({ length: 4 }, () => []) は、長さ 4 の配列を作り、各要素を 2 番目の関数の戻り値で埋めます。ここでは空の配列 [] が 4 つ入った配列になります。関数を毎回呼ぶので、4 つの [] はそれぞれ別の配列です。

文法: forEach

配列.forEach((要素, 番号) => { … }) は、配列の要素を先頭から 1 つずつ関数に渡して呼びます。map と違い、新しい配列は作りません。

文法: 条件演算子 ? :

条件 ? A : B は、条件が真なら A、偽なら B になる式です。L61 の note.duration > 0 ? 2 : 1 は「ロングノーツなら 2、タップなら 1」です。

コンストラクタは、new GameSession(譜面のノーツ, レーン数, 再生速度) で呼ばれたときに 1 回だけ動き、欄の最初の値を作ります。src/game/engine.ts の L53 が new GameSession(chart.notes, chart.lanes, opts.settings.rate) と呼んでいます。

  1. L53-55 生のノーツを PlayNote に作り直し、時刻順（同じ時刻ならレーン順）に並べる。index には元の位置を残す。
  2. L56 全ノーツの状態を "pending" にする（map で同じ長さの配列を作る）。
  3. L57 レーン数ぶんの空の列を作る。
  4. L58 各ノーツの番号 i を、そのノーツのレーンの列に入れる。時刻順に回るので、各列も時刻順になる。this.lanes[note.lane]?.push(i) の ?.（文法の索引の『オプショナルチェーン ?. と ??』）は、レーン番号が範囲外で列が無ければ何もしない、という意味です。
  5. L59 カーソルを全レーン 0（先頭）にする。
  6. L60 押し続けているロングノーツは全レーン null（無し）にする。
  7. L61 判定の総数を数える。reduce（文法の索引の『map・filter・reduce』）で、タップは 1、ロングノーツは 2 を足していく。

ロングノーツを 2 つに数えるのは、始点と終点で別々に判定するからです（docs/design.md の 6 節）。例えば「エリーゼのために」の EASY はノーツが 184 個で、そのうち 5 個がロングノーツなので、total は 184 + 5 = 189 です。

L52 のコンストラクタ引数 private readonly rate = 1 は、引数として受け取ると同時に this.rate という欄にもする書き方です（文法の索引の『private とコンストラクタ引数のプロパティ』）。rate は再生速度で、0.5 なら半分の速さで遊んでいることを表します。

文法: != null

JavaScript には「値が無い」ことを表すものが 2 つあります。わざと「無い」を入れた null と、まだ何も入っていない・存在しない番号を読んだときの undefined です。

x != null（= が 1 つ少ない「緩い」比べ方）は、x が null でも undefined でもないとき真になります。両方をまとめて調べたいときに限って、!== ではなくこちらを使うのが定番です。

L71–L74

realMs は、曲の時間差（秒）を実際の時間のミリ秒に直します。

再生速度 rate が 1 未満のとき、曲の 1 秒は実際には 1 / rate 秒かかります。例えば rate が 0.5 なら、曲の 0.021 秒の差は実際には 0.042 秒、つまり 42 ms です。判定幅（PERFECT ±42 ms など）は人間の手の感覚の話なので、テンポを落としても実際の時間で同じ幅にしたい。そこで、時刻の差を rate で割ってから judge.ts の判定に渡します（docs/design.md の 6 節）。

private なので、このクラスの中からだけ使えます。

71 
72 private realMs(songSeconds: number): number {
73 return (songSeconds / this.rate) * 1000;
74 }

L75–L87

文法: 計算された欄の名前

L77 の { ...this.counts, [judgement]: this.counts[judgement] + 1 } を分けて読みます。

  • ...this.counts は、今の counts の欄を全部写します（文法の索引の『スプレッド構文 ...』）。
  • [judgement]: 値 の角括弧は、「変数 judgement の中身を欄の名前にする」書き方です。judgement が "great" なら great: 値 と書いたのと同じです。後ろに書いた欄が前の同じ名前の欄を上書きするので、その 1 つだけが 1 増えた新しいオブジェクトになります。

record は判定 1 つを記録します。

  1. L77 その判定の数を 1 増やす。
  2. L78 判定済みの数を 1 増やす。
  3. L79 スコアの元になる得点に、判定の重み（PERFECT 1、GREAT 0.75、GOOD 0.35、MISS 0。judge.ts の L16）を足す。

L112–L121

release(lane, songTime) はレーンを離したときの処理です。押し続けているロングノーツが無ければ null（タップのノーツは離しても何も起きません）。

ロングノーツの途中なら、終点の時刻 note.time + note.duration から離した時刻を引いた「どれだけ早く離したか」を実時間のミリ秒で求め（L118）、それが 150 ms（HOLD_RELEASE_TOLERANCE_MS、judge.ts の L14）以下なら PERFECT、それより早ければ MISS にします。終点の判定は PERFECT か MISS の 2 通りだけです。

150 ms の猶予があるのは、終点ぴったりまで押し続けるのは難しく、少し手前で離すのが自然だからです。tools/chart.py も、ロングノーツの終わりを鍵盤を離す位置より 0.06 秒手前にして、次のノーツとの間を空けています（types.ts の L13-15 の解説）。

L119 の const judgement: Judgement = … は、変数に型を書いて作る形です。条件演算子の結果を「Judgement 型」として持ちます。

文法: forEach の中の return、while の中の continue と break

  • forEach に渡した関数の中で return すると、その要素の処理だけが終わり、次の要素に進みます（L135）。forEach 全体は止まりません。
  • continue は、while の残りを飛ばして次の繰り返しに進みます（L145）。
  • break は、while の繰り返しそのものを抜けます（L148）。

update(songTime) は時間が進んだことの処理で、engine.ts の tick（L186）が毎フレーム、その時点の曲の位置を渡して呼びます。前半と後半の 2 つの仕事をします。

前半（L134-138）: 押し切ったロングノーツ。 押し続けているレーンを全部見て、曲の位置が終点の時刻を過ぎていれば、終点を PERFECT で確定させます。離すまで待たずに成功にするので、押しっぱなしでも次のノーツの判定に響きません。

後半（L139-156）: 見逃したノーツ。 レーンごとに、カーソルの位置から順にノーツを見ていきます。

  1. L143-146 判定済みのノーツは飛ばす（カーソルを進めて continue）。
  2. L148 まだ判定していないノーツについて、曲の位置がノーツの時刻から実時間で 125 ms（WINDOWS.good）を過ぎていなければ break して、このレーンは終わり。列は時刻順なので、これより後ろのノーツはもっと先にある。
  3. L149-152 過ぎていれば見逃しとして "done" にし、MISS を記録する。ロングノーツなら終点の分の MISS も記録する。結果は始点の 1 つだけ返す。
  4. L153 カーソルを進めて次のノーツへ。

L155 で、進めたカーソルを覚えておきます。こうしておくと、次のフレームでは判定済みのノーツを見直さずに済みます。

見逃しの境目を MISS の幅（160 ms）ではなく GOOD の幅（125 ms）にしているのは、125 ms を過ぎたらもう GOOD 以上は取れないので、その時点で MISS を確定させてコンボの表示を早く切るため、と読めます（※ 推測）。
