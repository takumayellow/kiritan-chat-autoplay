src/game/engine.ts

takumayellow/syncadence-v2 の main（404da56）の写し。コードは 1 文字も変えていない。右の解説はこのサイトだけのもの。

1 プレイ分の進行役 PlayEngine です。曲の 0 秒をいつ鳴らすかを決めて音を予約し、入力の時刻を「そのとき聞こえていた曲の位置」に直して判定に回し、毎フレーム描画に渡す材料をまとめます。

このファイルが担うもの

  • 開始: 音の時計（AudioContext）を動かし、曲の 0 秒を鳴らす時刻を決めて SongClock を作る（start、L80-90）。
  • 音の予約: 毎フレーム、少し先までの曲の音をピアノの音源で予約する（tick の L183 から EventScheduler 経由、実際に鳴らすのは sound の L75-78）。
  • 判定: キーやタッチの時刻を、入力の補正を入れた曲の位置（judgeTime、L121-125）に直して GameSession に渡す（press / release、L145-159）。見逃しやロングノーツの終わりは毎フレーム確定させる（L186）。
  • オートプレイとキー音（叩いたときだけ鳴る音）（L161-175, L127-139）。
  • 一時停止: 音の時計を止め、描画の時刻を止めた瞬間に固定する（pause / resume / pausedAtMs）。
  • 描画の材料: 表示の補正を入れた曲の位置、押しているレーン、判定の光などを 1 つの Frame にまとめる（frame、L194-215）。

判定の幅やスコアの計算は src/game/session.ts と src/game/judge.ts、時計の換算は src/audio/clock.ts、絵を描くのは src/render/highway.ts の仕事です。このファイルはそれらを時刻でつなぐ役です。

読みどころ

  • start の L85-89。曲の 0 秒を鳴らす AudioContext の時刻を 1 つ決める式です。この 1 つの数から、音の予約・判定・描画の時刻がすべて決まります。

  • tick（L178-192）。1 フレームでやることの順番（時計の合わせ直し → 音の予約 → オートプレイ → 見逃しの確定 → 終わりの判定）。
  • pausedAtMs（L39, L95, L103, L195）。一時停止中にノーツが流れ続けないための 1 つの変数です。

3 つの時刻（先に読んでください）

このファイルには、物差しの違う時刻が 3 種類出てきます。取り違えると全部が分からなくなるので、先に整理します。

物差し 単位 どこで出てくるか 性質
performance.now() ミリ秒 描画のループの時刻（nowMs・drawMs）、入力の e.timeStamp、判定の光の atMs ページを開いてからの経過時間。細かく、止まらず、巻き戻らない
AudioContext の currentTime 秒 ctx.currentTime、startContextTime、音を鳴らす時刻 when 音を作る仕組みの時計。音の部品を 128 サンプル（48 kHz なら約 2.7 ms）ずつ作るので刻みが粗い。suspend() すると止まる
曲の位置 秒（曲の中の時間） ノーツの時刻 note.time、音の開始 event[0]、judgeTime、Frame.songTime 楽譜の上の時刻。テンポ rate を 0.75 にすると、曲の 1 秒が実時間の 1/0.75 ≈ 1.33 秒になる

音の時計と曲の位置は、start で決める startContextTime（曲の 0 秒を鳴らす AudioContext の時刻）でつながります。

  • 曲の位置 → 音の時計: startContextTime + 曲の位置 / rate（src/audio/clock.ts の L65-67、contextTimeOf）
  • 音の時計 → 曲の位置: (音の時計 − startContextTime) × rate

performance.now() と音の時計は、SongClock が毎フレーム対応を取ります（src/audio/clock.ts の L15-28, L44-51）。ブラウザの getOutputTimestamp() は「いまスピーカーから出ている音は、音の時計でいうと何秒のものか」と「それは performance.now() でいうと何ミリ秒か」の組を返します。その差 offset を覚えておけば、どの performance.now() の時刻についても、そのとき聞こえていた曲の位置を

曲の位置 = (offset + performance.now() / 1000 − startContextTime) × rate

で出せます（songTimeAt、src/audio/clock.ts の L58-62）。ctx.currentTime は「いま作っている音」の時刻で、スピーカーから聞こえるのはそれより出力の遅れ（数 ms〜数十 ms、Bluetooth なら 100 ms を超えることも）だけ後です。判定と描画は聞こえている位置、音の予約は作っている位置を基準にする、というのがこのファイルの使い分けです。

落とし穴

  • 一時停止の直後は、曲の位置がわずかに先へ飛ぶことがあります。 pause は ctx.suspend() の完了を待たずに pausedAtMs を記録します（L95-96）。止まるまでの間に音の時計が少し進むと、その分だけ再開後の位置が、止めた瞬間に描いていた位置より先になります。※ 推測: 止まるまでの時間はブラウザ次第で、どれくらい進むかは測っていません。
  • tick は、片付け（dispose）の後に呼ばれると true（曲が終わった）を返します（L180）。いまは Play.tsx が片付けと同時に描画のループを止めるので問題になりませんが、ループを止めずに片付けると結果画面へ進んでしまいます。
  • オートプレイも入力の補正の影響を受けます（L184-185）。オートプレイは補正を入れた judgeTime がノーツの時刻を過ぎたら押すので、入力の補正を +50 ms にしていると、聞こえている音より 50 ms 遅れて押します（判定は PERFECT のまま）。

L17–L21

文法: 説明コメント /** */

// は行末までのコメント、/* … */ は範囲のコメントです。/** と星を 2 つにして始めると、すぐ下の関数や変数の説明書きとして扱われ、エディタでその名前にマウスを重ねたときに表示されます。動きには関係しません。

eventTimeMs(timeStamp, nowMs) は、入力イベントの時刻 e.timeStamp を信じてよいかを確かめ、だめなら今の時刻で代わりにします。

信じる条件は 3 つ全部です（&& で「かつ」）。

  1. timeStamp > 0 — 0 や負の値ではない
  2. timeStamp <= nowMs + 1 — 未来ではない。1 ms までは丸めの誤差として許す
  3. nowMs - timeStamp < 1000 — 1 秒以上前ではない

条件 ? timeStamp : nowMs で、満たせば timeStamp、満たさなければ nowMs を返します（文法の索引の「条件演算子 ? :」）。

なぜ要るのか。 いまのブラウザでは e.timeStamp は performance.now() と同じ物差しですが、古いブラウザには 1970 年からのミリ秒（数兆という大きな数）を入れるものがありました。それを曲の位置に直すと、とんでもない値になって判定が壊れます。条件 2 がそれを弾きます。条件 3 は、タブを裏から戻した直後などに古いイベントが届いたときの備えです。

export が付いているのは、タイミングを測る画面（src/ui/Calibrate.tsx の L66）でも同じ確かめをするためです。

18/** 入力イベントの時刻を performance.now() の時間軸で返す。壊れた値は今の時刻で代用する。 */
19export function eventTimeMs(timeStamp: number, nowMs: number): number {
20 return timeStamp > 0 && timeStamp <= nowMs + 1 && nowMs - timeStamp < 1000 ? timeStamp : nowMs;
21}

文法: class と constructor

class 名前 { … } は、同じ形の物を作るための設計図です。設計図には次の 2 つを書きます。

  • 中身（フィールド）: その物が持つ値。L33-47 の session・lanes・clock など
  • メソッド: その物にできること。L75 の sound、L80 の start など。関数と同じ書き方で、function を付けない

new PlayEngine({ … })（Play.tsx の L58）と書くと、設計図から物（インスタンス）が 1 つ作られます。作るときに 1 回だけ動くのが constructor（L49-69）です。

メソッドの中の this は「いま操作されている、その物自身」です。this.lanes は「この進行役のレーン数」、this.handle(…) は「この進行役の handle メソッドを呼ぶ」という意味になります。

フィールドに = 値 を書くと、それが最初の値になります（L37 の clock は null、L40 の stateValue は "ready"）。値を書かないフィールドは、constructor の中で必ず入れます。

private は L49-69 の囲みで説明します。readonly は「作った後は入れ替えない」印です（文法の索引の「interface と readonly」）。

for (const x of 配列) { … } は、配列の要素を先頭から 1 つずつ x に入れて、中を繰り返します。番号を使わず要素だけが欲しいときの書き方です。L62 は 2 重になっていて、「譜面のノーツ 1 つずつについて、そのノーツが鳴らす音の番号 1 つずつを、集合に入れる」です。

キー音の仕組み（L59-66）。 譜面のノーツ 1 つ 1 つは [時刻, レーン, 長さ, 鳴らす音の番号の並び] の形で（src/song/types.ts の RawChartNote）、4 番目が曲の音のリスト events の何番目の音を担当するかを指します。キー音を使うときは、それらの番号を keysounds に集めて予約係に渡します。予約係はこの集合に入っている音を予約しません（src/audio/scheduler.ts の L23）。その音は、ノーツを叩けたときにだけ handle（L129-135）が鳴らします。

文法: map・filter・reduce

配列から別の値を作る道具です。どれも元の配列は書き換えません。

書き方 結果 例
a.map(f) 各要素に f を当てた結果の、同じ長さの新しい配列 [1,2,3].map((x) => x * 2) → [2,4,6]
a.filter(f) f が真を返した要素だけの新しい配列 [1,2,3].filter((x) => x > 1) → [2,3]
a.reduce(f, 初め) 初め から始めて、要素を 1 つずつ f(これまで, 要素) でまとめた 1 つの値 [1,2,3].reduce((s, x) => s + x, 0) → 6

始める位置 startSong（L88）

startSong = min(0, 最初のノーツ − ノーツが流れてくる時間 × rate, 最初の音) − LEAD_IN × rate

ノーツは、判定線に届く approachSeconds（実時間、既定 1.6 秒）前に奥に現れます。曲の時間に直すと approachSeconds × rate です。min の中の 3 つは「曲の 0 秒」「最初のノーツが奥に現れる位置」「最初の音」で、そのいちばん早いものから、さらに LEAD_IN（実時間 0.8 秒）分さかのぼった位置から始めます。こうすると、時計が動き出してから 0.8 秒は何も起きず、その後に最初のノーツが現れるか最初の音が鳴ります。

時計の起点（L89）

startContextTime = ctx.currentTime + START_DELAY − startSong / rate

時計の起点 startContextTime は「曲の 0 秒を鳴らす音の時計の時刻」です。上の式は、「いまから 0.15 秒後（START_DELAY）に、曲の startSong 秒の位置にいる」ように決めています。曲の位置を音の時計に直す式 startContextTime + 曲の位置 / rate に startSong を入れると、ctx.currentTime + 0.15 になることで確かめられます。

数で追うと（既定の設定、テンポ 100%、最初のノーツが 1.2 秒、最初の音が 0 秒の曲）:

  • startSong = min(0, 1.2 − 1.6, 0) − 0.8 = −0.4 − 0.8 = −1.2
  • startContextTime = ctx.currentTime + 0.15 + 1.2 = ctx.currentTime + 1.35
音の時計 曲の位置 起きること
currentTime + 0.15 −1.2 秒 時計の起点。何も無い
currentTime + 0.95 −0.4 秒 最初のノーツが奥に現れる
currentTime + 1.35 0 秒 曲の最初の音が鳴る
currentTime + 2.55 1.2 秒 最初のノーツが判定線に届く

なぜ START_DELAY が要るのか。 時計を作った直後の currentTime ちょうどに鳴らす音を予約しても、予約が届く頃には音の時計はもう先へ進んでいて、鳴らし損ねます。0.15 秒の余裕を取り、最初の予約が必ず未来の時刻になるようにしています。

L119–L125

判定に使う曲の位置です。perfMs は performance.now() の物差しの時刻（入力なら e.timeStamp、毎フレームの処理なら描画の時刻）です。

judgeTime = (その時刻に聞こえていた曲の位置) − 入力の補正(ms) / 1000 × rate

入力の補正（inputOffsetMs、−300〜+300 ms）は、音が聞こえてから押すまでのずれを打ち消します。正の値にすると、判定に使う位置が手前（早い側）にずれるので、「聞こえた音より遅めに押しても合う」ことになります。たとえば +30 ms なら、ノーツの音が聞こえてから 30 ms 後に押したときに差が 0 になります。

補正はミリ秒（実時間）で持っているので、/ 1000 で秒に、× rate で曲の時間に直してから引きます。テンポ 50% のとき、実時間の 30 ms は曲の時間の 15 ms です。

時計がまだ無い（開始前）なら -Infinity を返します。GameSession.press はこれをどのノーツからも遠すぎる押下とみなして無視します（src/game/session.ts の L99-101、判定の幅の外は null）。

この値はタイミングを測る画面（src/ui/Calibrate.tsx）や結果画面の提案（src/ui/Result.tsx の L27, L74）で決まります。どちらも「押した時刻 − 正しい時刻」の中央値を使います（src/game/stats.ts）。タイミングを測る画面は測った中央値をそのまま補正にし（src/ui/Calibrate.tsx の L115）、結果画面の提案はいまの補正に中央値を足します（src/ui/Result.tsx の L74）。

利用者のキー入力は、オートプレイ中は判定に使いません（L148, L156）。押したレーンは一瞬光りますが、次のフレームで L174 が上書きします。

L176–L192

毎フレーム呼ばれる進行です。Play.tsx の L82 から、描画のループの時刻 nowMs（performance.now()）で呼ばれます。曲が終わったら true を返します。

  1. プレイ中でなければ何もしない（L180）。開始前・一時停止中は false、終わった後は true を返す
  2. 時計を合わせ直す（L181）。clock.update が performance.now() と音の時計の対応 offset を測り直し、揺れをならす
  3. 音を予約する（L183）
  4. 判定に使う曲の位置を出す（L184）
  5. オートプレイなら押す（L185）
  6. 時間経過の判定（L186）。判定の幅（125 ms）を過ぎても押されなかったノーツを MISS にし、押し続けて終わりまで来たロングノーツを PERFECT にする（src/game/session.ts の L132-158）。結果は 1 つずつ handle へ
  7. 終わりの判定（L187-190）。全部のノーツが判定済みで、聞こえている位置が endTime を過ぎたら finished にして true を返す

3 の予約の基準（L183）。 予約係に渡すのは

(ctx.currentTime − startContextTime) × rate

で、これは音の時計がいま作っている曲の位置です。判定や描画に使う「聞こえている位置」は、これより出力の遅れの分だけ遅れています。予約は「これから作る音」を決める作業なので、作っている位置から 0.4 秒先（src/audio/scheduler.ts の L13 の lookahead、曲の時間）までを予約します。聞こえている位置を基準にすると、出力の遅れが大きい端末（Bluetooth など）では予約が遅れて、鳴らすべき時刻を過ぎてしまいます。予約係は 0.05 秒より古くなった音を鳴らさずに飛ばします（同 L23）。

7 で songTimeAt を使う理由。 終わりの判定には入力の補正を入れない、聞こえている位置そのものを使います。余韻（TAIL_SECONDS）を実際に聞かせてから結果画面へ進むためです。

178 tick(nowMs: number): boolean {
179 const clock = this.clock;
180 if (!clock || this.stateValue !== "playing") return this.stateValue === "finished";
181 clock.update(nowMs);
182 // 予約は「いま聞こえている位置」ではなく AudioContext の現在時刻から先を見る
183 this.scheduler.pump((this.opts.ctx.currentTime - clock.startContextTime) * clock.rate);
184 const t = this.judgeTime(nowMs);
185 if (this.opts.settings.autoplay) this.autoplay(t, nowMs);
186 for (const result of this.session.update(t)) this.handle(result, nowMs);
187 if (this.session.finished && clock.songTimeAt(nowMs) >= this.endTime) {
188 this.stateValue = "finished";
189 return true;
190 }
191 return false;
192 }

描画の材料をまとめます。 Play.tsx の L96 から、描画のループの時刻 drawMs で呼ばれ、結果は drawFrame（src/render/highway.ts の L408）へ渡ります。

描く時刻（L195）: 一時停止中なら pausedAtMs、それ以外は drawMs です（?? は左が null なら右、文法の索引の「オプショナルチェーン ?. と ??」）。理由は L91-97 の解説を見てください。

聞こえている位置 heard（L200）

  • 時計がある（開始後）なら、clock.songTimeAt(nowMs)
  • 開始前なら、「最初のノーツの時刻 − ノーツが流れてくる時間」。READY の画面では、最初のノーツがちょうど奥の端にいる絵になる

描画に使う曲の位置 songTime（L204）

songTime = heard − 表示の補正(ms) / 1000 × rate     （開始後だけ）

表示の補正（visualOffsetMs、−300〜+300 ms）は、音と絵のずれを打ち消します。正の値にすると、描く位置が少し前の曲の位置になるので、ノーツはまだ奥にいるように描かれ、判定線に届くのがその分だけ遅れます。画面の表示が音より遅れる端末（テレビにつないだときなど）では、音がノーツより先に聞こえるので、表示の補正で合わせます。

入力の補正と表示の補正は混ざりません。 入力の補正は judgeTime（L124）だけに、表示の補正はこの songTime だけに入ります。表示の補正を変えても判定は変わらず、入力の補正を変えてもノーツの見た目の位置は変わりません。音の予約にはどちらも入りません。補正を音と絵で分けるのは、ほかのリズムゲーム（taiko-web・Bemuse・Quaver）と同じ考え方です（docs/research/03-web-audio-timing.md）。
